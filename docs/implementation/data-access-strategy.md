# Data Access Strategy

**Document Status:** Draft  
**Version:** 1.0  
**Owner:** DiaperScout Project  
**Last Updated:** 2026-08-02

---

# 1. Purpose

This document defines how DiaperScout interacts with persistent data.

The objective is to provide a data access approach that is:

- Simple
- Maintainable
- Performant
- Testable
- Aligned with the domain model

Data access should support the business model rather than dictate it.

---

# 2. Philosophy

DiaperScout models the business domain using C# objects.

Persistence is an implementation detail.

Developers should primarily think in terms of:

- Products
- Reviews
- Observations
- Scouts
- Manufacturers

rather than:

- Tables
- Rows
- Foreign keys

The database exists to persist the domain—not define it.

---

# 3. Entity Framework Core

Entity Framework Core is the primary data access technology.

Reasons for selection include:

- Strong .NET integration
- Excellent tooling
- Migration support
- LINQ querying
- Mature ecosystem

Entity Framework Core is considered an abstraction over SQL rather than a replacement for SQL.

Developers are expected to understand the SQL generated by Entity Framework Core.

---

# 4. PostgreSQL

PostgreSQL is the platform's sole relational database.

The implementation intentionally embraces PostgreSQL capabilities where they provide clear benefits.

Examples include:

- Full-text search
- Trigram similarity
- Advanced indexing
- JSON support
- Extensions

Database portability is not considered a project objective.

---

# 5. Domain First

The domain model should drive the database design.

Entity Framework Core exists to map the domain model to PostgreSQL.

The database schema should not become the primary design artefact.

---

# 6. Query Philosophy

Queries should express business intent.

Preferred:

```csharp
FindProductByBarcode(barcode)
```

Rather than thinking in SQL terms.

Developers should write expressive LINQ queries while remaining conscious of the SQL generated beneath them.

---

# 7. SQL Awareness

Entity Framework Core should never be treated as magic.

Developers should understand:

- Generated SQL
- Execution plans
- Index usage
- Query performance

Performance issues should be investigated at both the Entity Framework and PostgreSQL levels.

---

# 8. Raw SQL

Entity Framework Core should remain the default approach.

However, raw SQL is appropriate when:

- Performance requires it.
- PostgreSQL features are unavailable through LINQ.
- Reporting queries become excessively complex.
- Database administration requires direct SQL.

Raw SQL should be the exception rather than the rule.

---

# 9. Migrations

Database schema changes should be managed exclusively through Entity Framework Core migrations.

Schema changes should:

- Be version controlled.
- Be repeatable.
- Be reviewed.
- Be tested.

Manual database modifications should be avoided outside exceptional operational circumstances.

---

# 10. Images

Large binary assets should never be stored within PostgreSQL.

Instead:

- PostgreSQL stores metadata.
- Cloudflare R2 stores image files.

Image categories include:

## Product Images

- High quality
- Curated
- Long-term

## Observation Images

- Evidence-based
- Optimised for storage
- Associated with observations

---

# 11. Search

Product search should initially use PostgreSQL capabilities.

Expected technologies include:

- Full-text search
- Trigram similarity
- Appropriate indexing

Dedicated search infrastructure should only be introduced if PostgreSQL becomes an identified bottleneck.

---

# 12. Dependency Injection

Application components should depend upon abstractions representing business capabilities rather than concrete persistence implementations.

Where appropriate:

- Services should be injected.
- Entity Framework Core should remain within Infrastructure.
- Business workflows should remain persistence-agnostic.

---

# 13. Future Evolution

Future enhancements may include:

- Read replicas
- Archival strategies
- Search indexing
- Analytics databases

Such additions should extend the existing strategy rather than replace it.

---

# 14. Design Philosophy

Data access should feel like working with the DiaperScout domain rather than working with a database.

Developers should spend their time thinking about products, reviews and observations—not SQL syntax.

At the same time, the implementation should never lose sight of the database beneath the abstraction.

Understanding both Entity Framework Core and PostgreSQL is considered an important part of building a performant, maintainable platform.
