# Installed iOS PWA startup investigation — 1 October 2026

## Outcome and boundaries

The complete physical-iPhone failure has **not** been reproduced or conclusively diagnosed. The user reports iOS 27.0.1, a newly installed Home Screen icon, a persistent branded splash and the red Blazor error banner. Testing found a reproducible production circuit-initialization failure and a verified production defect: the three Web replicas use **disjoint, container-local Data Protection key rings**. This is different from the previously observed negotiation/transport 404 connection-ID failure. It is strong infrastructure-side evidence, not proof that every iPhone failure has this cause.

No production code/configuration was changed and no image was deployed. The user explicitly required stopping/reporting when evidence points to infrastructure. A speculative PWA rewrite, automatic reload, shared hard-coded encryption key or weakened authentication would not be a safe fix. No infrastructure, scaling, affinity, database, TLS, auth or cache-policy changes were made. API scale-to-zero is enabled and deliberately unchanged; API cold-start latency remains a separate consideration.

## Reproduction and evidence

Installed Playwright's WebKit 26.6 build 2359 for investigation; Playwright version 1.63.0. Tests use its iPhone 13 device profile, touch/mobile viewport and an injected `navigator.standalone` flag. This is **desktop WebKit with simulated standalone detection**, not iOS 27.0.1 or a real Home Screen app. Native app lifecycle, iOS storage separation and background/restore behavior cannot be fully emulated.

1. Production comparison: WebKit and Chromium, browser and standalone, each visiting Explore, Products and a real MEGAMAX Black variant. All twelve page observations reached readiness, removed the cover and had no visible error banner or recorded application/transport errors. Workers were active. [Comparison evidence](ios-startup-evidence/browser-comparison.json).
2. Production persisted WebKit profile: register/control the worker, close/restart the browser across three launches, navigate Explore → Products → back. One launch recorded `The circuit failed to initialize`, `Circuit host not initialized` and an invocation canceled because the connection closed. This happened on the interactive journey; the initial static Explore page and subsequent restored Explore did not remain covered. Two later launches recorded no errors. This reproduces a production framework failure, **not the entire reported cold-launch symptom**. [Persisted-profile evidence](ios-startup-evidence/persistent-webkit.json).
3. Single-server local WebKit comparison: both browser and standalone startup/navigation passed with real Blazor and isolated test data. There are no multiple replicas in this test. This argues against a consistently reproducible standalone-only JavaScript incompatibility in the available WebKit engine; it does not rule out a physical iOS issue.
4. Read-only inspection of key-file identifiers on all three Web replicas found one different key per replica and no overlap. Only filenames were listed: no XML contents or key material were read. Sanitized server logs showed missing-key-in-key-ring cryptographic exceptions during antiforgery cookie deserialization, plus a warning that keys live in a container-local directory which may not persist. A missing-key event at 11:32:35 UTC (12:32:35 London) followed the persisted-profile circuit failure recorded at 11:32:32 UTC. Temporal proximity supports investigation but does not prove that the same request produced both errors. [Key-ring evidence](ios-startup-evidence/key-ring-evidence.json).

The missing-key exceptions observed in logs are **antiforgery** exceptions. They are not a captured Blazor descriptor-decryption exception; the antiforgery implementation can regenerate an unreadable cookie. This distinction matters. Per-replica key separation independently creates a concrete risk for protected descriptors, cookies and restart behavior, but the precise server-side reason for the captured failed circuit remains unconfirmed. Two subsequent replica-log reads failed with Azure log-auth-token conflicts; earlier successful reads and all three filename comparisons are recorded. Absence of a descriptor exception in limited logs is not proof that none occurred.

## Application review

- **Standalone detection:** display-mode media query or `navigator.standalone === true`. It changes presentation/install hints, not endpoints, authentication, SignalR transport or Blazor startup options. The full-screen startup cover is standalone-specific; normal Safari leaves SSR content visible while initialization is pending. Consequently an underlying initialization failure can be much more obstructive in installed mode. Static SSR content looking usable alone does not prove circuit health.
- **Manual startup:** framework script has `autostart=false`; lifecycle code starts it once after the document completes. Circuit options use the correct Web App `circuit` property. The splash introduces no extra circuit. Framework `start()` resolves before asynchronous server circuit initialization completes; readiness therefore depends on `onCircuitOpened` for interactive pages. A rejected server initialization does not fire that callback. The existing slow/45-second failure path remains; there is no blind retry. A future improvement could integrate the framework fatal-error signal directly into branded failure presentation, but that would improve error handling rather than establish or fix this iPhone's underlying failure.
- **Service worker:** exact nine-asset static/offline allowlist, no query-string/static-variant caching, network-authoritative application navigation, no dynamic/auth/admin/commerce cache. No old application HTML or component descriptors are intentionally cached. Persisted-worker launches were exercised. No caching policy was changed.
- **Enhanced navigation:** chrome is restored after DOM changes and enhancedload; existing history regression waits for actual interactivity after reload. Persisted WebKit navigation was exercised. No forced full navigations or retry workaround was added.
- **Passkeys:** initialization waits for the framework event API and reloads lists replaced by SSR markup. Standalone mode does not change credential requests/cookie handling. Existing virtual-WebAuthn regression remains in the full suite. A Home Screen app can have different native storage context from Safari; physical-device validation is still required.
- **API scale-to-zero:** expected and unchanged. Cold API startup can delay interactive catalogue responses. No API keep-alive, warmer, replica change or timeout workaround was introduced. The verified key-ring mismatch concerns Web replicas and is independent of expected API idling.

## Why the key-ring defect matters

ASP.NET Core protects server-component descriptors before sending them in SSR HTML. A receiving server must unprotect them before accepting components. Different key rings mean a payload issued by replica A cannot be read by replica B. Authentication/antiforgery cookies also rely on Data Protection. Fresh app storage, independent connections, restarts and restored navigation can change which server receives a request. This mechanism does not require a WebSocket HTTP 404.

Primary implementation references: [.NET 10 descriptor validation](https://github.com/dotnet/aspnetcore/blob/v10.0.0/src/Components/Server/src/Circuits/ServerComponentDeserializer.cs), [circuit startup/error handling](https://github.com/dotnet/aspnetcore/blob/v10.0.0/src/Components/Web.JS/src/Platform/Circuits/CircuitManager.ts), [Web App startup](https://github.com/dotnet/aspnetcore/blob/v10.0.0/src/Components/Web.JS/src/Boot.Web.ts).

A proper remediation requires durable shared Web Data Protection keys, consistent application isolation and protected key storage, while preserving existing authentication. That requires separately authorized configuration/storage work and validation across replicas/restarts. It must not be replaced with a fixed secret, bypassed validation or weaker cookies. This investigation did not perform that remediation or change session affinity.
